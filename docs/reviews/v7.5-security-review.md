# v7.5 security review

The checklist is `docs/handoff/v7.5-plan.md` §2. Each item ends as **pass**, **fixed (commit)**, or
**accepted risk** (the owner's decision, with the reason). This file collects the results. It starts with
the known limits of what v7.5 built (26 Nov 2026); the rest is filled in by the release review.

## Known limits (accepted for v7.5)

| # | Limit | Risk | Why accepted, and what would change it |
|---|---|---|---|
| L1 | **Two-step sign-in is checked by the app only.** A password alone still opens the API (PostgREST, Realtime) to that member's RLS; MaxOff's screens and actions are closed to it | Medium: the Owner's RLS includes money | The advisor's decision for v7.5. Follow-up: ADR-0018 (draft), a database check of `aal`, which touches every RLS path |
| L2 | **A TOTP code can be used twice within its 30 seconds.** GoTrue accepted one code for two sessions in the same window (local probe, 26 Nov 2026); no GoTrue setting changes this | Low: a code needs the password first and lives about 30 s | MaxOff does not build its own TOTP check (advisor). Each verify upgrades only the session that sent it (GoTrue binds the challenge to that session's token), so one verify never counts for another session |
| L3 | **Two browsers verifying the same factor at the same moment can fail** inside GoTrue (a deadlock: `/challenge` 500, SQLSTATE 40P01) | Low: one person, one device at a time | The app shows an error, never "wrong code", and Continue works on the next tap. Seen locally at 3 Playwright workers; CI runs one worker per shard |
| L4 | **The CSP is report-only, with `script-src 'unsafe-inline'`** | Low while report-only: the policy blocks nothing | The owner's decision (Q7): a week of reports, then enforced. Enforcing a script policy needs per-request nonces (ARCHITECTURE §18.3) |
| L5 | **A refusal the database simply filters is not counted** for the daily probe note (a direct API read that RLS answers with no rows) | Low: the app's own refusals are counted, and that is where a person probes | The database cannot count its own refusal: the raise rolls its own transaction back (plan §2.8) |
| L6 | **Sign-in records, attendance and the rest are not deleted when their period ends** | Low until the periods pass | Invariant 9; any automatic deletion needs an ADR and the owner's explicit OK (`docs/PRIVACY.md`) |

## Blocking before the tag

- **Supabase production TOTP enabled, the Owner confirms** (plan §7). Without it the Owner, the only person
  who approves deploys, cannot pass the second step that production requires. Recovery:
  `docs/runbooks/two-step-sign-in.md` §4.
