### 2.2 Access control (OWASP A01): the RLS sweep
- [ ] **Every table has RLS on.** Today 69 of 69 public tables. A pgTAP check that fails on a new table without it (extend `00_core_base`).
- [ ] **A generated role × table matrix:** for each of the 69 tables, each role reads, inserts, updates and deletes what PERMISSIONS says, and nothing more. The roles: Owner, Admin, Crew, a Crew coordinator of a freelancer, a freelancer, a deactivated member, anon, and a member of a **second organisation**. Built from PERMISSIONS as data, so a policy drift fails a test. The tables with no policy (hand-in, upload links, money) must show zero rows to every API role.
- [ ] **Column grants:** every `grant update (…)` matches the columns the screens edit (v5.0's `has_handin` grant is the example to follow).
- [ ] **Money isolation (invariant 2):** re-run the money pgTAP for every path (tables, views, functions, Realtime publications, search, exports), plus a grep of Admin and Crew payloads for money fields.
- [ ] **Server actions and route handlers:** each starts with `requirePermission` (or a transition function that checks); a lint rule that flags an action or `app/api/**/route.ts` without one; IDOR checks on every `[id]` route (another organisation's id → NOT_FOUND).

- [ ] **Realtime:** each channel's filter cannot be widened by the client; a member subscribed to another organisation's topic receives nothing.

### 2.3 SECURITY DEFINER audit (the member_back_on lesson)
- **Today (`main`, 26 Nov):** 318 security-definer functions (147 `app`, 171 `public`). **All 318 pin `search_path = ''`; none is executable by `anon` or PUBLIC.** The API role (`authenticated`) may run 154 `public` ones (the app's calls; each checks its caller, directly or through a shared `app.*_caller` / `require_*` helper) and 50 `app` ones; 17 `public` ones (the jobs: claims, digests, file bookkeeping, `bootstrap_owner`) are service_role only. `app` is not exposed through the API (`supabase/config.toml` schemas), so its grants matter only inside SQL.
- [x] **The catalog test** (`supabase/tests/175_v75_definer_audit.test.sql`, `phase-v75`): every definer pins `search_path` to empty; none runs for anon or PUBLIC; service_role runs all; and the definers the API role may run are **exactly** two explicit lists (`api_app`, `api_public`), every overload alike. A new definer granted to `authenticated` without being listed fails (v6.5's `app.member_back_on` would have), as does Supabase's default grant on a new `public` function. **When a branch adds an API function, it adds the name to the list in the same change.**
- **Fixed (advisor's decision, 26 Nov): migration `v75_definer_grants`** makes both groups below service_role only (`api_app` is now 21 names). Before it:
  1. 13 `app` definer helpers the API role may run that no policy, view, invoker function, default or check calls as the caller: `admin_client_ids`, `attendance_require_decider`, `directory_visible`, `expenses_require_decider`, `field_definition_has_values`, `is_approving_admin`, `is_working_day`, `lock_client_for_edit`, `project_visible`, `push_endpoint_valid`, `require_client_manager`, `require_team_manager`, `stage_group_label`. They could be service_role only (they are reachable only from SQL, so the risk is low; `lock_client_for_edit` returns a whole `clients` row past RLS). Revoking needs `00_core_base`'s `app_internal` list updated and any pgTAP that calls them as `authenticated` checked.
  2. 16 `app` definer **trigger** functions hold `authenticated` EXECUTE (`audit_row_change`, the guards, `seed_org_*`, `task_comments_notify`…). Harmless (a trigger function cannot be called directly, and EXECUTE is checked only at `create trigger`); tidy-up only.
- For **each**:
  - [ ] `set search_path = ''`;
  - [ ] the **first** statements check the caller (`app.current_member()`), the permission key, and the **organisation** of every id it is given;
  - [ ] no EXECUTE for `anon` unless public by design (invite acceptance);
  - [ ] dynamic SQL only through `format()` with `%I` / `%L`.
- [ ] **A pgTAP rule:** every `app` function that checks no permission is service_role only (the `app_internal` list), and the list's count is asserted, as `00_core_base` does today. Extend it to `public`: a definer without `app.has_permission`, `app.current_member` or a documented exception fails.
- [ ] **A review aid:** a query listing each definer, its grants, and whether its body calls a permission helper, attached to the review.
- [ ] Triggers that are security definer: the audit trigger cannot be used to write arbitrary history rows.

## 4. Database and speed: candidates (10.4)

Each candidate is measured first (`pg_stat_statements` on staging; the probe on the routes). It is kept only if it helps, and never adds a read to a shared layout.

1. **The slowest queries:** the top 20 by total time on staging (after a day of the team's use), each with `EXPLAIN (ANALYZE, BUFFERS)`.
2. **Missing indexes:** Supabase's advisor ("unindexed foreign keys", "unused indexes") plus the foreign keys on `activity_log`, `notifications`, `task_assignees`, `handin_files` and `leave_requests`.
3. **The RLS helpers' cost:** `app.task_visible`, `app.has_permission` and `app.current_member` per row on the big lists, with `(select …)` wrapping where it isn't yet.
4. **Growth:**
   - `activity_log` and `notifications` row counts, and their size per month;
   - partitioning `activity_log` by month if it passes ~1 M rows;
   - the existing 90-day read-notification removal checked.
5. **Pagination:**
   - People (134 rows in local test data; the real team is ~15, so it's low risk);
   - `/tasks/all`, a client's history, Approvals with many items: cursor pages where a list can pass ~200 rows.
6. **Bundles:**
   - the heaviest routes (`/people` 895 KB, `/approvals` ~849 KB, `/tasks/[id]` 830 KB) for code that can load after the page;
   - budgets are never raised.
7. **Worker cold start:** the 2.8 measurement repeated (the Worker grew with Drive and uploads).
8. **Realtime:** the number of channels per page, and the payload size.
