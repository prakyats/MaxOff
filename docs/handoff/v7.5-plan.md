# v7.5 "Polish and security": the plan

> **Status: PROPOSED (builder, 26 Nov 2026). Docs only; no code until the owner's "proceed v7.5".**
> Sources: `docs/ROADMAP.md` phase 10 (10.2 UX polish, 10.3 security review and DPDP, 10.4 performance); `docs/handoff/release-plan.md` (v7.5, about 1.5 weeks; after v7.0 "Reliable anywhere", before v8.0 "Full launch").
> What v7.0 already covers is not repeated here: iPhone and accessibility tests in CI, real-user speed, every screen's skeleton on the tap, and v7.0's "security hardening" carry-overs. v7.5 is the **full** review.
> **Found while writing this (26 Nov):** `next` 16.3.5 on `main` has critical advisories. One of them (RCE in the Image Optimization API) may be reachable through `/_next/image`. It is raised to the advisor as a **hotfix now**, not left for v7.5 (§2.1).

## 1. Units

| Unit | What | Size |
|---|---|---|
| **A · Security review** (10.3) | The checklist in §2, every finding fixed or written down with the owner's decision. Expand-only migrations for grant or policy fixes, with pgTAP for each role. | 4–5 days |
| **B · DPDP privacy** (10.3) | The staff privacy notice (§3: text for the owner's approval, then a lawyer's check), where it shows, a retention rule per kind of record, and the written answers to a member's requests. | 1–2 days |
| **C · Database and speed** (10.4) | The candidates in §4: slow queries, indexes, list pagination, bundle and cold start. Every change is measured before and after with the probe. | 2–3 days |
| **D · UX polish** (10.2) | The keyboard audit of every screen, empty / loading / error states, a phone pass at 375 and 430, accessibility fixes. Through the design tools where the session has them, else by hand with screenshots (as in v5.0 and v6.5). | 2–3 days |

The order is A → B → C → D. Security first, because a finding can change a screen.

## 2. Security review checklist

Every item ends as **pass**, **fixed (commit)**, or **accepted risk (owner's decision, with the reason)**. The finished checklist goes into `docs/reviews/v7.5-security-review.md`.

### 2.1 Dependencies (OWASP A06)
- **Today (`pnpm audit --prod`, 26 Nov):** 56 advisories (4 critical, 15 high, 31 moderate, 6 low).
  - Critical: `next` ≤ 16.4.0 (RCE in the Image Optimization API; RCE in `use cache`), `next` 16.2–16.3.5 (RCE in `next/og`), `@sentry/nextjs` < 10.75.2 (tunnel-route bypass).
  - We use none of `use cache`, `next/og` or a Sentry tunnel. **`/_next/image` is let through by `src/proxy.ts` and nothing disables the optimizer: treat it as exposed until checked.**
  - High: `zod` < 4.6.6 (memory exhaustion: zod checks every server action), Server Actions DoS (`next`), `undici`, `sharp`, `body-parser`, `source-map-js`.
  - **Hotfix proposed separately (advisor, 26 Nov):** bump `next`, `@sentry/nextjs` and `zod`; set `images.unoptimized`.
- **v7.5 adds:**
  - [ ] a CI step `pnpm audit --prod --audit-level=high` that fails the build;
  - [ ] a dependency update routine (Renovate, or a monthly by-hand pass; Q3);
  - [ ] the dev-only advisories (`@modelcontextprotocol/sdk`, `systeminformation`) checked to be out of the Worker bundle.

### 2.2 Access control (OWASP A01): the RLS sweep
- [ ] **Every table has RLS on.** Today 69 of 69 public tables. A pgTAP check that fails on a new table without it (extend `00_core_base`).
- [ ] **A generated role × table matrix:** for each of the 69 tables, each role reads, inserts, updates and deletes what PERMISSIONS says, and nothing more. The roles: Owner, Admin, Crew, a Crew coordinator of a freelancer, a freelancer, a deactivated member, anon, and a member of a **second organisation**. Built from PERMISSIONS as data, so a policy drift fails a test. The tables with no policy (hand-in, upload links, money) must show zero rows to every API role.
- [ ] **Column grants:** every `grant update (…)` matches the columns the screens edit (v5.0's `has_handin` grant is the example to follow).
- [ ] **Money isolation (invariant 2):** re-run the money pgTAP for every path (tables, views, functions, Realtime publications, search, exports), plus a grep of Admin and Crew payloads for money fields.
- [ ] **Server actions and route handlers:** each starts with `requirePermission` (or a transition function that checks); a lint rule that flags an action or `app/api/**/route.ts` without one; IDOR checks on every `[id]` route (another organisation's id → NOT_FOUND).
- [ ] **Storage:** R2 objects private; signed URLs short-lived; the avatar and receipt paths are not guessable; receipts readable only by their member and the Owner (invariant 2's exception).
- [ ] **Realtime:** each channel's filter cannot be widened by the client; a member subscribed to another organisation's topic receives nothing.

### 2.3 SECURITY DEFINER audit (the member_back_on lesson)
- **Today:** 384 security-definer functions in `public` and `app`; 171 of the `public` ones are callable by `authenticated`.
- For **each**:
  - [ ] `set search_path = ''`;
  - [ ] the **first** statements check the caller (`app.current_member()`), the permission key, and the **organisation** of every id it is given;
  - [ ] no EXECUTE for `anon` unless public by design (invite acceptance);
  - [ ] dynamic SQL only through `format()` with `%I` / `%L`.
- [ ] **A pgTAP rule:** every `app` function that checks no permission is service_role only (the `app_internal` list), and the list's count is asserted, as `00_core_base` does today. Extend it to `public`: a definer without `app.has_permission`, `app.current_member` or a documented exception fails.
- [ ] **A review aid:** a query listing each definer, its grants, and whether its body calls a permission helper, attached to the review.
- [ ] Triggers that are security definer: the audit trigger cannot be used to write arbitrary history rows.

### 2.4 Injection and XSS (OWASP A03)
- [ ] Every `dangerouslySetInnerHTML` (a grep; the guide and the notes' links are the likely ones) is reviewed or removed. Links in notes and chat stay `http(s)` only, `rel="noreferrer"`.
- [ ] File names (hand-in, upload link, receipts) are never put into HTML or `Content-Disposition` unescaped.
- [ ] Every dynamic SQL in migrations goes through `format()` (a grep for `execute` in function bodies).

### 2.5 Configuration and headers (OWASP A05)
- **Today:** HSTS (2 years, subdomains), `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` (camera, microphone, geolocation off), and a CSP of `frame-ancestors 'none'` only.
- [ ] **A full CSP** in report-only for a week (Sentry collects the reports), then enforced:
  - `default-src 'self'`; `script-src` with nonces;
  - `connect-src` Supabase, R2, Google upload, Sentry;
  - `img-src 'self' data: blob:` plus R2;
  - `object-src 'none'`, `base-uri 'none'`.
- [ ] `X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-site`.
- [ ] **Supabase Auth settings:** leaked-password protection on, the minimum password length matches the app's rule, the JWT expiry, sign-ups disabled (invite-only), email change re-confirmation.
- [ ] **Cloudflare:** production's Worker has no preview URLs (`preview_urls: false`, checked), WAF managed rules on, Bot Fight mode decided (Q4).

### 2.6 Authentication and sessions (OWASP A07)
- [ ] Rate limits: sign-in, password reset, invite acceptance, the hand-in and upload-link start endpoints, and the cron routes (CRON_SECRET compared in constant time). Cloudflare rate-limit rules where the app has none.
- [ ] "Sign out of this device" and the Owner's deactivate end every session (refresh tokens revoked).
- [ ] Invite links: single use, expiry, and no account enumeration in the messages.
- [ ] The Owner's account: two-factor sign-in (Q2).

### 2.7 Secrets and integrity (OWASP A02, A08)
- [ ] A secret scan of the whole git history (gitleaks); a hit is rotated, not only deleted.
- [ ] An inventory of every secret (Supabase secret key, `DRIVE_TOKEN_KEY`, Google OAuth, Resend, VAPID, `CRON_SECRET`, `SESSION_IP_HASH_SALT`, Sentry): where it lives (GitHub environment, Worker secret), who can read it, and a rotation plan (Q5).
- [ ] GitHub: the `production` environment's required reviewer is the Owner (checked); actions pinned by commit SHA; no workflow gives write tokens to `pull_request` code.
- [ ] The service worker caches nothing personal (the instant-skeleton spec already checks the prefetch payloads).

### 2.8 Logging and monitoring (OWASP A09)
- [ ] Sentry scrubbing: user id only, no email, IP, task titles or money (the existing `scrub.ts` tests, extended to the new modules: hand-in, upload link, Drive).
- [ ] Every mutation is audited (a trigger or a transition function): a pgTAP that every table with an UPDATE grant has `audit_row_change` or a documented reason (hand-in tables: their functions write the history).
- [ ] An alert when a member is refused FORBIDDEN many times in a short time (a possible probe; Q6).

### 2.9 SSRF (OWASP A10)
- [ ] `/_next/image` closed (§2.1).
- [ ] The Worker only fetches Google's and Supabase's hosts; Drive file ids and resumable-session URIs are checked against Google's host before use.

## 3. DPDP: the staff privacy notice (draft for the owner to approve)

**Where it shows:** **Me → Privacy** for everyone, and a one-time "Read how MaxOff uses your information" card after the first sign-in. The guide links to it. The owner approves the text; a lawyer checks it before v8.0 (Q1).

> **Your information in MaxOff**
>
> MaxOff is Pixora Clips' internal app for running the studio's work. This note says what it keeps about you, why, and for how long.
>
> **What we keep**
> - Your name, work email, phone number, photo (if you add one), role and job title.
> - Your attendance: when you start and end your day, breaks, and corrections.
> - Your leave and comp leave requests and their decisions.
> - Your extra work and expense claims, with the receipts you upload.
> - The tasks you work on, your notes, your chat messages, and the files you hand in (these go to the studio's Google Drive).
> - Basic sign-in records: when you signed in, and a scrambled form of your device's internet address, so we can spot misuse.
>
> **Why**
> To pay you correctly, plan the studio's work, approve leave and expenses, and keep the app secure. We don't sell your information or use it for advertising.
>
> **Who can see it**
> - The Owner sees everything.
> - Admins see your work, your availability (not your leave reasons) and your tasks.
> - Your expense claims are seen only by you and the Owner.
> - Our service providers store it for us: Supabase (database), Cloudflare (hosting and files), Google (Drive), Resend (email) and Sentry (error reports, without your name or email).
>
> **How long**
> - While you work with us, and afterwards for as long as the law and the studio's accounts need it: attendance, leave and expense records for ‹8 years›, tasks and chat for ‹3 years›.
> - Your account is then deactivated and your personal details are removed where the law allows. (The periods are for the owner to set and the lawyer to confirm: Q1.)
>
> **Your rights**
> You can ask to see what we keep about you, to correct it, or to have it removed when we no longer need it. You can also complain to the Data Protection Board of India.
>
> **Questions**
> Contact ‹the Owner's name and email›, who looks after your information for Pixora Clips.

**The written retention rule per record** goes into `docs/PRIVACY.md` (Q1 sets the periods). Each period gets a scheduled job only after v8.0. **Nothing is deleted before then** (invariant 9), and any removal follows invariant 9's rules: archived first, permanent delete Owner-only.

## 4. Database and speed: candidates (10.4)

Each candidate is measured first (`pg_stat_statements` on staging; the probe on the routes). It is kept only if it helps, and never adds a read to a shared layout.

1. **The slowest queries:** the top 20 by total time on staging (after a day of the team's use), each with `EXPLAIN (ANALYZE, BUFFERS)`.
2. **Missing indexes:** Supabase's advisor ("unindexed foreign keys", "unused indexes") plus the foreign keys on `activity_log`, `notifications`, `task_assignees`, `handin_files` and `leave_requests`.
3. **The RLS helpers' cost:** `app.task_visible`, `app.has_permission` and `app.current_member` per row on the big lists, with `(select …)` wrapping where it isn't yet.
4. **Growth:**
   - `activity_log` and `notifications` row counts, and their size per month;
   - partitioning `activity_log` by month if it passes ~1 M rows;
   - the existing 90-day read-notification removal checked.
5. **Pagination:**
   - People (134 rows in local test data; the real team is ~15, so it's low risk);
   - `/tasks/all`, a client's history, Approvals with many items: cursor pages where a list can pass ~200 rows.
6. **Bundles:**
   - the heaviest routes (`/people` 895 KB, `/approvals` ~849 KB, `/tasks/[id]` 830 KB) for code that can load after the page;
   - budgets are never raised.
7. **Worker cold start:** the 2.8 measurement repeated (the Worker grew with Drive and uploads).
8. **Realtime:** the number of channels per page, and the payload size.

## 5. UX polish (10.2)
- **The keyboard audit** of every screen: tab order, focus after each action, Escape and Enter as ARCHITECTURE §14.3 says, and the calendar's keys. Findings fixed in the shared controls first.
- **Every screen's empty, loading, error and no-permission states** listed and checked against the Definition of Done.
- **A phone pass** at 375 and 430 (light and dark) for every screen: clipped controls (like v5.0's "Leave out" found in its design pass), truncation that hides the key fact (like v6.5's Team today time), and 44 px targets.
- **Accessibility:** contrast measured for every text token in both themes; screen-reader names for icon buttons; the reduced-motion setting respected.
