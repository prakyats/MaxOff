## 1. The importer for existing clients and projects

**What it is.** It loads the studio's existing clients, their contacts and their running projects into MaxOff once, so the team stops keeping them in a sheet.
- It is for the Owner only. Reached from Settings → Import, on a phone or a laptop.
- It runs on **staging first**, on a copy of the real sheet. Production runs only after the owner checks the staging result.

**Input: two CSV files**, exported from a Google Sheet template MaxOff provides. One row per record. Headers are fixed, and unknown columns are refused by name.

| Clients | Required | Notes |
|---|---|---|
| `client_name` | yes | Unique, ignoring case, among clients not Inactive (kickoff 3 decision 1). |
| `legal_name`, `gstin`, `city`, `address`, `phone`, `email`, `website`, `drive_url` | no | The same checks as the client form (GSTIN format, `https://` only). |
| `admin_email` | yes | An active Admin. The client is theirs (`client_admin_assignments`). |
| `state` | no | `active` (default) or `draft`. |
| `contact_name`, `contact_phone`, `contact_email`, `contact_role` | no | Becomes the primary contact. More contacts are added in the app. |

| Projects | Required | Notes |
|---|---|---|
| `client_name` | yes | Must match a client in the file, or one already in MaxOff. |
| `project_name` | yes | |
| `recurrence` | yes | `one_time`, `weekly` or `monthly`. |
| `delivery_date` | one-time only | IST date (kickoff 7 (A)). |
| `template` | no | The name of an existing project template. Its stages and deliverables are used. |
| `stages`, `deliverables` | when no template | Separated by `|`, e.g. `Shoot|Edit|Review`. |
| `amount` | no | **The Owner's money (v2.1). Q3.** |

**How it works:**
1. **Upload.** The two files are parsed in the browser and checked against the columns. Nothing is written yet.
2. **Dry run (always first).** The server checks every row as the import would: names, Admins, templates, dates, duplicates. It shows a report:
   - the rows that **will be created**, per client with their projects;
   - the rows that **will be skipped** (already in MaxOff, matched by name, ignoring case);
   - the rows **refused**, each with the reason in plain words and its row number.
   - It writes nothing. "Download the report" gives the same as a CSV.
3. **Import.** One tap: "Import N clients and M projects". It runs through the existing transition functions (`client_create` / `client_activate` / `client_contact_*` / `project_create`, ADR-0006). Every record is therefore audited exactly as if typed in, permissions are checked, and nothing bypasses RLS.
   - It goes **one client at a time, each in its own transaction**. A refused client never half-creates its projects. The others carry on, and the report lists what failed.
4. **Idempotent re-run.** Each row's **import key** (a hash of the file's own key columns) is recorded in a new Owner-only table, `import_rows`: run id, sheet, row number, key, outcome, and the created entity id. Running the same file again skips what was already imported and reports it as "already imported". A corrected row with a new key is imported then.
5. **Audit trail.**
   - `import_runs` holds who ran it, when, which file (its name and SHA-256), dry run or real, and the counts.
   - The created records carry their normal `activity_log` rows, plus one "Imported from ‹file›, row n" entry each.
   - Nothing is ever deleted (invariant 9). A wrong import is fixed by archiving or editing, like any record.
6. **Notifications.** By default an import sends no per-record notifications. Each Admin gets one summary: "12 clients and 30 projects were imported for you" (Q4).
7. **Tests.**
   - pgTAP: both new tables' RLS for each role (the Owner only); the import function's paths (valid, a duplicate, an unknown Admin, a bad date, a re-run); idempotency.
   - Unit tests: the CSV parser and the row checks.
   - Playwright: the dry run, the import and the report at 375 / 430 / desktop.
   - A run on staging with the real sheet's copy.

New tables (expand-only, RLS in the same migration): `import_runs` and `import_rows`, both `settings.manage` (the Owner). Money columns are imported only through `modules/revenue` (invariant 2).

## 2. The guide-completeness audit

**Goal:** every screen, for every role that opens it, has a guide topic that matches today's app (owner 2026-10-15: "it should be up-to-date").
1. **Build the matrix:**
   - the routes come from `src/app/(app)/**/page.tsx`;
   - who opens each route comes from the nav (`NAV_BY_ROLE`) and the permission each page requires;
   - the topics come from `src/modules/guide/domain/content/{owner,admin,crew}.ts` (each topic's `link.href` and its shots' paths).
2. **Make it a test:** `guide-coverage.test.ts` fails when a route a role can open has no topic for that role. Routes with nothing to explain go on a short list of named exceptions (`/forbidden`, `/offline`, `/diagnostics/*`), each with a reason.
3. **Read every topic against the screen** on the staging preview, one role at a time. Fix the wording and re-shoot what changed (`pnpm guide:screenshots`, in the 11:15–17:30 IST window). List anything the guide says that the app no longer does.
4. **Out:** the matrix as a table in the release notes, every gap closed, and the test green.

**The gap list today** (`tests/guide-coverage.test.ts`, `KNOWN_GAPS`; main 3d237d0): the routes no topic of that role links to. Some are tabs that a parent topic describes without a link of its own; the audit decides each one, either a link on the topic that describes it or a new topic.
- **Owner (12):**
  - a client's Activity, Brand, a contact, the Projects list and a project page;
  - a person's Profile, Attendance, Leave and Month tabs;
  - `/reports` (the list itself) and a past day's End of day;
  - Settings → Company.
- **Admin (9):**
  - a client's Activity, Brand, a contact, the Projects list and a project page;
  - Leave → Expenses and My Day (an Admin can open both);
  - a person's Profile;
  - Settings → Custom fields.
- **Crew (1):** Tasks → All tasks.

## 3. The second restore drill (runbook `backup-restore.md`, due by the end of December 2026)
On the owner's laptop, like the first production drill (30 Sep 2026), with the newest nightly backup:
1. Make an empty directory and download and decrypt the newest backup from the production bucket. The steps and commands are in the runbook's "Restore" section, and the key stays in the owner's password manager.
2. Start a fresh `supabase/postgres:17.x` container (the version production runs) and restore with `AUTH_MODE=schema` as `supabase_admin`.
3. Verify:
   - every table's row count equals the backup's manifest;
   - the migration list ends at production's last migration;
   - RLS refuses anon and a JWT-less `authenticated`;
   - the expected pg_cron WARNING lists the scheduled jobs.
4. **New since the first drill:**
   - check that the newest tables (v2.1's money tables, `import_runs`) restored with their row counts;
   - time the whole restore, since the dump has grown;
   - restore one uploaded file (a receipt) from R2's file bucket to prove files come back too.
5. Write the row into "Drills done": date, backup key, counts, warnings, time. Then throw the container away.
6. If any step fails, fix the runbook the same day, and the drill counts only once it passes.

## The owner's questions (recommendation first)
1. **Where does the existing data live today?** (a) **Recommended:** one Google Sheet. We send a template with the two tabs above and someone copies the data in. (b) Several files or WhatsApp lists: we'd build the sheet together first.
2. **Which projects come in?** (a) **Recommended:** only projects that are **running now**, starting from the current month's cycle. Finished ones stay in the old sheet. (b) History too, as completed projects with no cycles.
3. **Import the project amounts?** (a) **Recommended:** yes, an optional `amount` column, counted from the current month on (Q1). Imported only when the Owner runs the import. (b) No: enter amounts by hand in each project's Billing section.
4. **Tell the Admins?** (a) **Recommended:** one summary notification per Admin, no per-record ones. (b) None. (c) Every record notifies, as if typed in.
5. **New clients' state.** (a) **Recommended:** Active, with their Admin. (b) Draft, so each Admin activates their own.
6. **A client already in MaxOff with the same name.** (a) **Recommended:** skip it and say so in the report. Its projects attach to the existing client. (b) Refuse the whole file.
7. **The restore drill date:** a weekday in mid-December, 30–45 minutes on the owner's laptop. Which day suits you?
